# 挂号抢号 JMeter 并发测试

## 这个测试验证什么

多个不同患者同时请求同一个排班，验证下面三件事：

1. 成功挂号数量不能超过测试前的剩余号源。
2. 测试后的剩余号源不能小于 0。
3. `成功挂号数量 + 最终剩余号源` 必须等于初始剩余号源。

测试计划会自动登录管理员、创建独立的测试患者、并发调用 `POST /registrations`，最后调用排班详情接口自动核对结果。

## 运行前准备

1. 启动 MySQL、Redis、RabbitMQ 和后端服务。
2. 在管理端准备一个日期未过期、状态正常、还有剩余号源的排班。
3. 记下该排班的 ID。第一次建议把排班总号源设置为 5，并使用 20 个并发线程。
4. 只在开发数据库或测试数据库执行，因为测试会留下名称以 `JMeterTest-` 开头的患者和挂号订单。

## 第一次建议使用图形界面

打开：

`C:\Users\Administrator\Desktop\apache-jmeter-5.6.3\apache-jmeter-5.6.3\bin\jmeter.bat`

然后载入 `registration-concurrency.jmx`，在测试计划顶部的“测试参数”中填写：

- `adminUsername`：管理员用户名，默认 `admin`
- `adminPassword`：管理员密码，只填在本机，不要提交到 Git
- `scheduleId`：本次压测的排班 ID
- `threads`：并发请求数量，第一次填 `20`
- `rampSeconds`：在几秒内发出全部请求，第一次填 `1`

点击绿色启动按钮。执行结束后查看“汇总报告”，其中“自动校验：成功数与库存变化必须一致”应当显示成功。

## 正确结果示例

如果初始剩余号源为 5，并发请求数为 20，理想结果是：

- 业务成功数：5
- 售罄返回数：15
- 最终剩余号源：0
- 非预期错误数：0
- 是否超卖：否
- 自动校验：通过

售罄返回不是系统故障，而是库存保护生效。真正需要关注的是非预期错误、成功数超过库存，或者最终库存小于 0。
